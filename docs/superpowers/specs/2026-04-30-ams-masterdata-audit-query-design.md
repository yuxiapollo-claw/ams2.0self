# AMS 主数据导入、审计拆分、权限查询与申请交互设计

## 1. 背景

当前 AMS 已具备用户、部门、系统与权限、申请管理、审计日志、权限查询等基础能力，但这版系统仍存在四类明显缺口：

- 用户与部门主数据无法通过外部正式数据源批量维护，现有系统数据与真实组织数据容易脱节。
- 审计日志仍是单页通用视图，无法支撑“账号历史”和“基础信息管理历史”两类完全不同的追溯场景。
- 权限查询仍偏设备视角，缺少按“用户/部门”和“系统/权限”两个业务视角查询的能力。
- 权限申请树交互不够清晰，终节点选择、关键字定位和提交流程反馈都不足，已经影响实际使用。

本次设计基于当前 AMS 代码线继续增强，不回到后续偏离的“目标系统 1:1 复刻”版本。目标是在现有版本上补齐主数据导入、历史追溯、查询聚合和申请交互，形成可以持续上线迭代的业务底座。

## 2. 本次设计目标

- 以当前代码结构为基础完成“用户/部门主数据”的正式导入能力。
- 将“审计日志”拆分为“账号历史”和“基础信息管理”两类独立页面与独立数据口径。
- 将“权限查询”拆分为“用户权限查询”和“系统用户查询”两个业务页面。
- 修复并重构“申请管理”下三类权限树操作的交互闭环。
- 为后续正式导入真实组织数据保留批次、错误明细、字段级历史追溯能力。
- 控制改造范围，不推翻现有登录、权限申请、系统/权限模型和基础 CRUD 骨架。

## 3. 明确确认的业务规则

以下规则已经在本轮设计阶段确认，后续实现与测试均以这些规则为准：

- 导入模式采用“增量合并”，不会因为 CSV 中缺少某条现存数据而自动删除系统内记录。
- 当系统内现有记录与 CSV 内容不一致时，以 CSV 为准覆盖映射字段。
- CSV 中的用户导入后直接成为可登录系统账号。
- 新导入用户统一使用同一个默认密码，并在首次登录时强制修改。
- 如果 `FireDate` 非空，或 `EmployeeStatusId` 表示离职/停用，则自动禁用登录账号，但保留人员、部门关联和所有历史记录。
- 部门导入以 `DepartmentNo` 作为外部唯一业务键。
- 用户导入以 `Initial` 作为登录名唯一业务键。
- CSV 文件按 GBK/CP936 编码读取，避免中文乱码。

## 4. 推荐方案与取舍

本次设计最终采用“主数据增强型”方案，即在现有 `sys_user / sys_department / access_request / audit_log` 基础上补充：

- 外部主数据映射字段
- 导入批次与错误明细
- 主数据历史表
- 账号历史事件表
- 查询聚合接口

### 4.1 采用该方案的原因

- 改动聚焦，能直接承接当前 AMS 版本，不需要重建整套用户与组织模型。
- 能同时覆盖 CSV 导入、主数据变更追溯、查询重构和申请交互修复。
- 对现有申请流程和系统权限模型冲击最小，上线风险低于重新分层建模。

### 4.2 未采用的方案

- 不采用“主数据/登录账号彻底分层重构”方案，因为会波及登录、用户管理、权限分配和审批链，超出当前可控范围。
- 不采用“只补页面不补模型”的轻量方案，因为会导致导入、历史和查询口径不一致，后续必然返工。

## 5. 当前系统现状与改造边界

### 5.1 当前可复用能力

- `sys_user` 已有登录账号、部门关联、账号状态、密码重置、管理员与个人改密能力。
- `sys_department` 已有部门维护、负责人维护、成员批量归属能力。
- `access_system / access_permission / user_permission_assignment / access_request` 已构成系统与权限申请主链路。
- 前端已具备审计页、查询页、申请工作台页等页面骨架。

### 5.2 当前主要不足

- 用户和部门缺少正式外部主数据映射字段。
- `audit_log` 仅能承载简单通用审计，不足以支撑业务历史查询。
- 查询页仍停留在单一设备节点视角。
- 权限树缺少搜索、高亮和明确提交流程反馈。

### 5.3 改造边界

- 不重做现有系统/权限树模型。
- 不重构现有审批状态机。
- 不在本轮引入复杂 BI 报表。
- 不在本轮做“全量替换式导入”或自动清理未出现在 CSV 中的历史主数据。

## 6. CSV 导入设计

## 6.1 数据源

本轮导入数据源固定为两份 CSV：

- `Departments_202604301114.csv`
- `Users_202604301116.csv`

两份文件都按 GBK/CP936 解码。

## 6.2 字段映射

### 6.2.1 部门 CSV

部门 CSV 关键字段：

- `Id`
- `DepartmentNo`
- `DepartmentName`
- `Company`
- `Site`
- `ParentId`
- `ManagerId`
- `StatusId`

映射规则：

- `DepartmentNo` 映射为部门外部编码，并作为导入匹配主键。
- `DepartmentName` 映射为部门名称。
- `ParentId` 作为外部上级引用，最终回填为系统内上级部门。
- `ManagerId` 作为外部负责人引用，最终回填为系统内负责人。
- `Company / Site` 作为组织附加属性保留。
- `StatusId` 映射为部门启用/停用状态。

### 6.2.2 用户 CSV

用户 CSV 关键字段：

- `Id`
- `Initial`
- `FirstName`
- `LastName`
- `DisplayName`
- `Title`
- `DepartmentId`
- `DepartmentNo`
- `DepartmentName`
- `ManagerId`
- `HireDate`
- `FireDate`
- `EmployeeTypeId`
- `EmployeeStatusId`
- `Company`
- `Site`
- `PhoneNo`
- `MobileNo`
- `Email`

映射规则：

- `Initial` 映射为 `loginName`，并作为用户导入匹配主键。
- `DisplayName` 映射为系统展示姓名。
- `FirstName / LastName / Title` 作为补充主数据保留。
- `DepartmentId / DepartmentNo` 映射为当前所属部门。
- `ManagerId` 映射为直属经理外部引用，后续回填为系统内用户。
- `HireDate / FireDate` 写入人事状态相关字段。
- `EmployeeTypeId / EmployeeStatusId` 作为原始枚举值保留，并映射出在职状态与是否禁用登录。
- `PhoneNo / MobileNo / Email / Company / Site` 作为联系方式与归属属性保留。

## 6.3 导入语义

- 采用增量合并。
- 同一部门以 `DepartmentNo` 匹配。
- 同一用户以 `Initial` 匹配。
- 命中现有记录时，按 CSV 覆盖映射字段。
- 未命中时新增记录。
- 不在 CSV 中的系统现有记录不自动删除。

## 6.4 新增账号规则

- 新导入用户自动创建系统登录账号。
- 默认密码统一由系统配置项提供。
- 新导入账号写入 `must_change_password = 1`。
- 首次登录后必须改密，成功后清除该标记。

## 6.5 停用规则

- `FireDate` 非空时自动禁用登录。
- `EmployeeStatusId` 命中离职/停用规则时自动禁用登录。
- 禁用只影响登录，不删除主数据和历史记录。

## 6.6 两阶段导入与回填

为处理 `ParentId`、`ManagerId` 等交叉引用，导入采用四步法：

1. 导入部门基础数据，不依赖负责人和上级是否已解析完成。
2. 导入用户基础数据与部门归属，同时创建或更新登录账号。
3. 回填部门负责人、上级部门、用户直属经理。
4. 写入导入历史、字段变更历史和错误明细。

## 8. 审计与历史页面设计

- `账号历史`

- 时间

## 10. 申请管理交互设计

申请管理保留三个子页面：

- `申请`
- `删除权限`
- `密码重置`

三页共用统一树形工作台框架，只是数据源与提交动作不同。

## 10.1 树形选择区

新增以下交互能力：

- 顶部关键字筛选框
- 关键字支持按系统名称、权限名称、完整路径模糊检索
- 命中节点自动展开祖先路径
- 已选节点使用整行高亮，不只依赖树组件默认 current-node 样式
- 最终权限节点显示显式标签
- 非最终节点显示“仅用于定位，不可提交”
- 禁用节点显示灰态和禁用说明

## 10.2 提交区

提交区保留“已选路径 + 原因输入 + 提交按钮”的结构，但要补齐状态说明：

- 未选节点时，明确提示“请先选择最终权限路径”
- 选中父节点时，提示“当前为父级节点，不可提交”
- 选中禁用节点时，提示“当前权限已禁用”
- 原因为空时，提示“请输入申请原因”

## 10.3 提交流程闭环

为解决“选择终节点后点击提交没有动作”的问题，提交流程必须可观测：

1. 点击提交前显示确认摘要。
2. 提交中按钮进入 loading 态。
3. 提交成功后显示成功反馈。
4. 新申请记录立即刷新到下方历史表。
5. 后端校验失败时，显示明确错误原因，如“已有未完成申请”。

## 10.4 各页差异

### 申请页

- 展示所有权限路径树。
- 只有最终权限节点可提交申请。

### 删除权限页

- 仅展示当前用户已拥有的最终权限树。
- 点击删除后发起权限删除申请，而不是直接删除。

### 密码重置页

- 仅展示当前用户已拥有的最终权限树。
- 点击密码重置后发起密码重置申请，而不是直接执行重置。

## 11. 用户与部门管理相关规则补充

本轮设计需兼容此前已确认的用户/部门管理规则：

- 用户管理页面不展示“用户编号”。
- 登录名必须唯一。
- 管理员可重置任意用户密码。
- 非系统管理员用户只能在自己的用户管理页修改自己的密码。
- 管理员可修改所有用户信息。
- 部门管理页面仅系统管理员可见。
- 字段“经理”统一改为“部门负责人”。
- 部门页支持指定负责人，也支持将用户批量加入部门。
- 一个用户同时只能属于一个部门。

- 页面新增/修改/停用部门

- CSV 导入新增部门
- CSV 导入更新部门字段

## 13.3 通用审计保留策略

- 现有 `audit_log` 保留，继续用于技术审计和基础行为追踪。
- 新业务页面优先读取专用历史表，不混读 `audit_log`。

## 14. 迁移与上线策略

## 14.1 迁移顺序

建议按以下顺序落地：

1. 数据库迁移，补齐主数据字段与新历史表。
2. 完成导入服务、枚举映射和批次逻辑。
3. 完成历史查询接口和权限查询接口。
4. 完成申请树前端重构与查询/审计页面重构。
5. 用正式 CSV 执行首批导入并完成核对。

## 14.2 首次导入策略

首次导入先执行“预演校验”，输出：

- 预计新增部门数
- 预计新增用户数
- 预计更新记录数
- 预计禁用账号数
- 失败行与原因

人工确认后，再执行正式导入。

## 14.3 首次导入后人工核对重点

- 系统管理员账号仍可登录。
- 随机抽样用户的登录名、姓名、部门、状态正确。
- 离职或停用用户已自动禁用。
- 部门负责人和成员归属正确。
- 基础信息管理页能看到本次导入导致的字段变更。

## 16. 风险与控制措施

### 风险 1：历史数据引用不完整

表现：

- 负责人、直属经理等外部引用在首次导入时可能存在部分无法回填。

控制措施：

- 保留 `source_manager_id`
- 记录失败明细
- 允许导入成功但回填失败的记录进入错误报告

### 风险 2：旧审计口径与新历史口径混淆

表现：

- 页面如果继续直接读取 `audit_log`，结果会与新历史页展示不一致。

控制措施：

- 新页面严格只读专用历史表
- `audit_log` 仅作为底层技术审计保留

### 风险 3：查询聚合性能下降

表现：

- 用户权限查询和系统用户查询在数据量增大后变慢。

控制措施：

- 对用户、部门、系统、权限关联字段补充必要索引
- 查询接口默认分页
- 下拉字典与查询结果分离加载

## 17. 实施顺序建议

建议后续实现计划按以下顺序拆分：

1. 数据库迁移与实体字段扩展
2. CSV 导入服务与批次/错误明细
3. 基础信息历史与账号历史写入
4. 权限查询聚合接口
5. 申请树交互重构
6. 审计区与查询区页面重构
7. 正式 CSV 导入与验收

## 18. 非目标

本轮明确不做：

- 现有权限模型的全面重构
- 审批状态机重做
- 未出现在 CSV 中主数据的自动清理
- 复杂 BI 图表中心
- 多租户或多组织层级平台化改造
